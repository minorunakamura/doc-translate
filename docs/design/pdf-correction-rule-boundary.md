## 2. 現状の3つの出口

初回PDF補正の採用（`pdf_correction._make_chunk` → `pdf_adoption.adopt_owned_ranges`）と組立（`pdf_source.assemble_pdf_source`）では、AIの補正案と抽出の差は次の3つのどれかになる。

| 出口 | 仕組み（事実） | 利用者への影響 | 費用 | 保守への影響 |
| --- | --- | --- | --- | --- |
| (a) ルールで採用・上書き | 補正案、抽出文字、原本PDFの描画を照合し、決定的な条件を満たせば採用する。現行は `ADOPTION_RULE = "adopted-edge-target-v17"`、chunk schema 18（`pdf_correction.py:34, 239`） | 条件が合えば正しい形で出る。誤適用すると、黙った誤接続や本文の改変になる | 追加の送信なし | ルールごとに分岐、拒否の対照、テスト、全70 chunk の再生、schema・方式名の更新が要る。行数の推移は §4.3 |
| (b) 抽出を残して `※` | `adopt_owned_ranges` 内の `issue(...)`（`CorrectionUncertainty`、`pdf_adoption.py:2464`〜）、`pdf_source.py` の `problem()`（stage `pdf_connection`、202 行〜）が保存を止めずに uncertainty を記録する。`render.py`（172 行〜, 512 行）で出力に `※` が付き、`units.py:408` で unresolved として扱われる | 本文は残り、該当箇所に `※` と QA の理由が付く。読者は原本を確認する手間がかかる。断片は分かれたまま出る | 追加の送信なし | 既存の理由文を再利用できる（例: "Unresolved {direction} code continuation"） |
| (c) 保存拒否 | `adopt_owned_ranges` 中の `raise ValueError`（例: 2831 "Overlapping ownership of extraction text" など）。`run.py:1044` で捕捉され、所有ページ（5ページ単位）が `failed_pages` になる | その5ページは出力されず、部分出力（§13 の「部分出力」）になる | `resume` で同じ5ページを再送するため再課金になる。再送で解消するかは未確認（§7） | 拒否を減らすには (a) のルール追加が必要になる。#101 では +1035 行だった（§4.3） |

要点（判断）: (b) は文字を落とさず断片を残す。(c) は情報を落とし、費用もかかる。(a) は利用者には最も良いが、保守コストは (a) に集まっている。

## 3. 判断基準（チェックリスト）

新しい不具合ごとに上から順に確かめる。**R** はルールを足す側、**M** は `※`（出口 b）で出す側に倒れる基準を表す。

1. **R: 読めた本文・数値・コード行の欠落、二重収録、改変を防ぐか。**
   なぜ: §6 は欠落や推測による補完を禁じている。欠落・二重・改変は `※` を付けても読者が気付きにくく、翻訳にも伝わる。
2. **R: 保存拒否（出口 c）を避けるのに必要か。**
   なぜ: 拒否されると5ページが丸ごと出力から消え、再送の費用もかかる。`※` で済む問題より害が大きい。
3. **R の前提: 抽出文字・出典ref・原本の描画だけで、結果が一意に決まるか。**
   なぜ: 一意でなければ、ルールは別の紙面で黙って誤る。誤接続・本文改変は黙って起きるが、`※` は読者の確認手間で済む。一意でない場合は (b) にする（§7「自動で片方を正しいと決めず要確認」）。
4. **M: 改善の対象が、見た目・整形（字下げ・空白数・空行・記号）や断片の接続か。**
   なぜ: これらは `※` で残しても文字は失われない。読者の手間と保守コストを比べると、手間のほうが小さいことが多い。
5. **M: 対象が特定の紙面・1書籍の1〜数か所だけか（一般的な文書構造の規則ではないか）。**
   なぜ: 1か所のための分岐は、他の書籍で効くかを確かめられないまま保守だけが残る。
6. **M: 座標・字送りの格子・描画枠など、幾何の推定に頼るか。**
   なぜ: 幾何の閾値はフォント・組版に依存し、誤適用したときの検出が難しい。#101 第4版では座標による位置決めを一度禁止した（#109 で限定的に解除）。
7. **M: 既存の安全側の拒否（例: #99 の誤target拒否）を緩めるか。**
   なぜ: 拒否は誤接続を防ぐために置いたものである。緩めると、守っていた失敗の形が再び出うる。

判定のしかた（判断）。1つの Issue に複数の項目があるときは、項目ごとに判定する:

- 1 か 2 に当たり、3 を満たし、4〜7 に当たらない → **ルールを足す**。
- 1・2 に当たらず、4〜7 のどれかに当たる → **`※` で出す**（ルールは足さない）。一般的な構造規則であっても同じ。
- 同じ項目が 1/2 と 4〜7 の両方に当たる、または 1/2 に当たるが 3 を満たさない → **境界**。扱いは都度ユーザーが決める。

## 5. ユーザーが選ぶ選択肢

### 案A: 現状維持（紙面ごとにルールを足し続ける）

- 利点: 見つかった紙面は最も良い形で出る。新しい判断の枠組みが要らない。
- 欠点: 1件ごとに分岐、拒否の対照、schema・方式名の更新、全70件の再生、原画像照合が要る。#109〜#111 は4組の接続（#109 の2組、#110・#111 の各1組。#110 は欠落・二重の解消を含む）のために、pdf_adoption.py で 480 行、pdf_source.py で 94 行と、schema 3世代（16〜18）を使った（§4.3、7e21f79〜60ee807）。別の書籍でどれだけ効くかは確かめられない。
- 既存ルール: そのまま残す。
- 今後の Issue: 接続・整形の不一致も、従来どおり個別の Issue と Planning でルール化する。

### 案B: データ保全と保存拒否の回避だけをルールで直し、接続・整形は `※` に寄せる

- 内容: §3 の基準 1・2 に当たり、3 を満たし、4〜7 に当たらないものだけにルールを足す。接続・字下げ・空白数・記号の差は、既存の uncertainty 理由文（出口 b）で `※` として出し、新しいルールは足さない。
- 利点: ルールが増えるのは、読者が気付きにくい害（欠落・二重・改変）と、費用のかかる失敗（拒否）に限られる。
- 欠点: #109・#111 のような接続できるはずの組も、今後は分かれたまま `※` 付きで出る。読者の確認の手間が増える。境界の Issue は都度の判断が残る。
- 既存ルール: 削除しない。#109〜#111 を含め現行の挙動を保つ。
- 今後の Issue: 接続・整形だけの不一致は「`※` で出ている、文字の欠落なし」を確かめたら、ルール追加なしで閉じる。欠落・二重・改変・拒否が見つかったら、データ保全の部分だけを Planning する。

### 案C: 案B に加えて、`※` 側に当たる既存ルールを将来の削除候補として記録する

- 内容: 案B の運用をしたうえで、§4 で `※` とした既存ルール（#97 の SPACE・字下げ、#98 の相対字下げ、#99 の接続、#100 の本文3組の接続、#109 の囲み、#110 の格子による空白数・接続、#111 の誤target緩和）を削除候補として一覧にし、境界とした既存ルール（#100 のダッシュ、#101 の p339・p179）は候補に含めるかを個別に決める。削除するかどうかは、各ルールの調査の後に個別の Work Item で決める。
- 利点: 保守コストの大きい層を実際に縮める道筋ができる。
- 欠点: 削除すると、該当箇所の出力が後退する（接続が切れ、`※` が増える）。削除は採用規則の変更になるため、新しい方式名・schema と、既存の保存済み chunk の扱い（旧ルールの再現をしないなら案内付きで止めるなど、項目4と同じ問題）が要る。各ルールが他の紙面の結果をどれだけ支えているかは未調査である（未確認、§7）。
- 既存ルール: 本書の段階では変更しない。候補の一覧化と調査は別の Work Item になる。
- 今後の Issue: 案B と同じ。加えて削除候補ごとの調査 Issue が生じる。

### 推奨（判断。決定ではない）

**案B を推奨する。** 理由:

- 直近の増分の大半は、データ保全か拒否回避の部分（#97・#108・#101）と、少数の紙面の接続・整形の部分（#109〜#111）に分かれる。後者は修正前も文字が失われておらず、`※` 付きで残っていた（Issue #109・#111 の本文）。
- 案B は §7 の「矛盾したら自動で片方を正しいと決めず要確認」「接続を確定できなくても本全体を止めず、原文断片と出典を保持する」と整合する。既存の設計（§13、§16）も確定できないものを `※` と QA で示すことを前提にしており、案B は新しい契約を作らずに運用できる。
- 案C は効果が大きいが、削除の影響（出力の後退、保存済み chunk の扱い）がまだ調べられていない。案B を採った後に、必要なら別途検討できる。

## 6. 既存設計との関係（指摘のみ、書き換えない）

- **§7 と #111 の関係（指摘）**: #111 は、片方向の target が相手の案と一致しない組を、狭い条件で接続する。§7 の「前後の継続情報が矛盾した場合は自動で片方を正しいと決めない」と緊張関係にあるように読める。#111 の Plan では「採用後の evidence との一致」を矛盾の解消と扱っており、ユーザー確認も得ている。矛盾かどうかの判断は本書ではしない。
- **§7 と出口 (c) の関係（指摘）**: §7 は接続について「本全体を止めない」と書くが、所有範囲が一意に決まらない場合の保存拒否（5ページ単位の失敗）については直接書いていない。「止めない」のはページ単位でも求められるのかは、既存文書からは決まらない。
- **§6 と #109 の関係（指摘）**: §6 は図について「近接や bbox の重なりだけで本文を除外しない」と書く。#109 の囲み判定は除外ではなく並べ替えと接続に描画枠を使うものなので、直接の矛盾はないと読んだ。

## 7. 未確認事項・限界

- 当てはめの根拠は、1冊の書籍（全70 chunk）を対象にした Issue とコミットだけである。他の書籍でどの基準に何件当たるかは未検証。
- 各既存ルールの削除可否、削除した場合に出力がどう変わるか、他の紙面の結果をどれだけ支えているかは調べていない（#101 第6版では、無効にしても全テストが通るのに実書籍の結果が変わる分岐があった）。
- 各ルールが現行の `pdf_adoption.py` の何行を占めるかは測っていない。
- 保存拒否された5ページを `resume` で再送したとき、同じ回答・同じ規則で再び拒否されるか、AI の回答が変わって通るかは未確認。
- `※` が増えたときの読者の確認負担は測っていない。目印の見やすさは §16 で未検証とされている。
- 本書の基準と分類は推奨である。境界とした項目の扱いは、ユーザーが案を選んだ後も Issue ごとに判断が要る。
