# #99 第3版：原本で確認できるコード全文を保存してから、ページ間を接続する

## 目的
[既存の #99](https://github.com/minorunakamura/doc-translate/issues/99) 一件で、接続前にコードが欠ける不具合を直す。完了とは、①原本で確認できる全文が採用chunkに保存され、別プロセスで読み直せること、②その全文が正しい相手との接続後も英語出力に一度だけ残ること。どちらか一方だけでは合格にしない。新しい先行Issue・中間commitは必要ない。

## 根拠と第2版からの変更
- 正式入力は [#99 第2版コメント](https://github.com/minorunakamura/doc-translate/issues/99#issuecomment-7018434061) と[第2版Plan](pdf-initial-source-preservation-99-r2.md)（SHA-256 `c48ac98cab76952621883cb2fc0fc289f05b22bbd28537d75299021d4daaf570`）。第2版の「#108の採用規則は不変」のうち、**新規方式で、抽出下書きの有効な文字範囲だけでは所有コードを保持できない場合**を本版で改訂する。旧版の再現、#108の役割分離、第2版の接続判定順・必須5組・禁止事項は維持する。過去のPlanやIssueコメントは編集しない。
- 停止根拠は `work/test-verification-99-r2-root-5g4SJdAF/direct.json`。同所の `verify_stop.py` と `proof/observations.json` で採用前後を追える。6 chunk（schema 12）で必須5組は接続したが、117–118の英語fenceは31行＋1行。118の保存回答は18行。欠けた非空白100字・171字は原本と保存回答にあり、118の他の出力blockにもない。assembleは既に短い断片を正しくつないでおり、ここでの文字追加は誤修正となる。

## 要件・決定事項
1. **新規採用は局所的な原本根拠で決める。** 入力は検証済み保存回答（または同じ契約の新規回答）のコード提案、元draftの出典、同一原本PDFと対応する検証済みページ画像。提案は候補であって正解ではない。所有ページ内の元のref・selector・位置に対応する可視の描画行について、文字・記号・行内空白・行順、行の前後と隣接範囲、既に採用できる部分との対応を確かめ、同じコード欄への所属と境界が一通りに決まる場合だけ採用する。複数refにまたがる場合も、全体を元順で重複なく照合し、離れた欄・別の所有者・脚注・caption・本文・callout・図表の内容を取り込まない。
2. **確実な文字と不確かな整形を分ける。** `orig`、ページ全体での文字列一致、空白除去後の一致、回答の主張、画像hashだけでは採用しない。不正spanを切り詰めず、`orig` を `text` の代用にせず、証明できない `text` のcharspanを作らない。出典は実際のpage・refと描画位置で辿れるようにする。所有・文字・順序が競合、不可視、対象外ページ、対応不能なら、その差分を補わず、既存の確実な内容・役割と位置付きQAを残す。逆に、所属と文字を証明できたのに、著者の絶対字下げや追加空行数が不明という理由だけで文字まで捨てない。紙面で確認できた行・相対位置を保ち、未証明の整形だけを位置付きQAにする。
3. **接続は[第2版の公開assemble期待表](pdf-initial-source-preservation-99-r2.md)どおり。** 採用前の提案と採用後の範囲の双方に対して相互target、draft間の実itemの同一性、selector、newline、kind/language・構造、ページ順・読順を調べる。介在や距離を使わず相互適合する相手を数え、両端で唯一の対に限り介在を検査する。空または元位置・所属で残せる独立脚注だけなら接続。本文・別コード・captionを飛ばさず、候補を消して再集計しない。採用で得た出典を理由に誤targetを救済しない。
4. **版は保存記録に従う。** 新規採用にのみ一つの後継方式を識別できるようにする。方式なし版1・名前付き旧版・`printed-roles-v10`（schema 11）・`reciprocal-code-v11`（schema 12）は元の採用規則とbyteを再現する。版12の第2版接続も保持し、後継版を古い接続判定へ落とさない。混在しても旧断片を昇格・再採用しない。未知方式・改変・再構成不一致は拒否し、方式追加だけでは旧成功を再送しない。

## 実装方針
- `fix/pdf-source-preservation` の現在の差分を出発点にする。新しいImplementationセッションが `git status`、追跡・未追跡差分と停止記録を最初に照合する。既存の接続・テスト・再生helperの部分実装を消して作り直さず、先行項目用に切り分けない。
- **先に採用を直す。** `src/doc_translate/pdf_correction.py` の `_make_chunk` から `pdf_adoption.py::adopt_owned_ranges` へ渡る既存の検証済み入力と、既存の局所描画行・位置の照合を利用する。新方式の所有コードだけに、上記を証明できた場合の採用経路を追加する。`_projection` の安全な入力制限は維持し、無効spanの本文や `orig` を送信しない。画像読出し・原本hash・回答検証を迂回しない。#108の共有出典の分割を広げず、既存のID・関係・位置QAを保つ。
- **次に接続から出力までを仕上げる。** `pdf_correction.py` の方式表・chunk契約・保存成功の再利用・orphan回収・load時の再構成、`pdf_source.py::assemble_pdf_source` のschema 12専用分岐とconsumerを確認し、後継方式を明示的に通す。run/resumeや候補採用の旧原文照合も記録自身の方式で行う。assemble、units、rendererに欠落文字を合成させない。
- 保存方式・原本根拠・互換性は `docs/reference/artifacts.md`、出力とQAの読み分けは `docs/reference/usage.md`、再生方法と採点は `.pi/skills/verify-project/SKILL.md` と同配下 `references/feature-map.md` に記す。`CONTRIBUTING.md` は正式チェックの入口が変わる場合だけ更新する。
