## 再計画の理由と変更点
- **停止理由（Implementation、Root が原本で直接確認）：** 第1版の前提「p213 の表の描画は全文字が等幅の格子に乗る」は誤りだった。
  - 罫線文字（`┌│┬─` など）の送り幅は 5.68pt で、英字の格子 4.672pt に乗らない。例：表の2行目の2本目の `│` は x=212.48（行頭から約 26.2 桁）。
  - `│` の後の隙間は、`│` の送りの終わり（生成空白の位置）から次の文字の原点まで測ると、格子のちょうど整数倍になる（例：95.68→212.48 は 25.0 桁）。この数は AI 案の空白数と、表の 19 行すべてで一致する。ただし抽出は、どの隙間も生成空白1つである。
  - そのため第1版の要件3（抽出と案の一致数だけ採用）を表に当てはめると、要件4（表を出典とするコードの描画確認）が成立しない。
  - p212 も同じ方法で測った。`→` の後は 1.00 桁、`✓` の後は全行で 2.00 桁、行内の連続空白（`Home  Starter` など）は 2.00 桁である。抽出と案は、`→`・`✓` の後とも空白1つである。
- **ユーザー判断（案B、確定）：** 格子外記号の直後の空白数を、描画で一律に確定する。記号の送りの終わりから次の描画文字の原点までが、格子の整数倍のときだけ採用する。抽出や案の空白数とは一致しなくてよい。整数倍でなければ、描画行を採用しない（現行の扱い）。
  - 結果として、p212 の `✓` の後は空白2つ（紙面どおり）になり、案（1つ）とは異なる。表の空白数は案と一致する。
  - 第1版の「抽出と案の一致数を採用し、空白幅が確定していない QA を付ける」はやめる。新しい QA は、下の要件3の1種類だけとする。
- **変えないもの：** 目的、保証の範囲（212→213 の1組、全変化を原画像で説明）、要件2・4〜7の内容、制約・対象外、TDD の対象、検証の分担。
- **既存の未コミット変更（保持する）：** 要件2の実装（`recover_listing`）、schema 17 と方式名 `drawn-table-listing-v16`（`pdf_correction.py`）、テスト `test_headed_listing_with_an_invalid_last_row_is_read_from_its_drawing`（`tests/test_pdf_correction.py`）。Implementation はこれを破棄せずに引き継ぐ。このテストのうち第1版の要件3に基づく部分（`SYMBOL_SPACE` の文言、`"symbol space"` を拒否とする期待、`✓` の後を1つとする期待）は、要件3（第2版）に合わせて改める。これは第1版の要件に従って Implementation 中に追加された未コミットのテストであり、制約「既存の正例・拒否例のテストの期待値は変えない」の対象外とする。

## 確認した事実（Planning で直接確認）
- 確認方法：最新の全70件再生（`work/preservation-all-9drsIXYe/proof/`、#109 の Root 検証、private）の source と chunk。保存済みの回答を現行製品で再採用する診断（メモリ上だけ、書き込みなし）。原本 PDF の pypdfium2 の文字位置。原画像（212–213枚目）。一時ファイルは `/tmp` だけに置いた。CodeGraph は未初期化のため同期を省略し、コードを直接確認した。
- **AI の回答は正しい。** `c212b` の案は 21 行（`newman` から `✓ home has property rel set to collection` まで）で、evidence は `#/texts/3302`（section_header）、`#/texts/3303`（code）、`#/texts/3304`（list_item、charspan 不正）。`c213a` の案は 19 行の表（罫線を含む）。どちらも、原本の描画文字と比べると、空白を除いた各行がすべて一致する。

  - `#/texts/3304` が list グループ `#/groups/77` の子で、読み順で `#/groups/77` が間に入る。
  - `#/texts/3302`（`newman`）が section_header である。
- **原因2（描画行の検証）：** 上の2点を診断で外しても、`_drawn_listing` が失敗する。

  - 行内の連続空白（`Home  Starter`、格子上 2 桁）は、抽出では生成空白1つになる。現行の比較は行頭の空白しか許さない。

- **原因3（表を出典とする続き）：** `c213a` は `#/tables/6` を出典とし、文字範囲がないので、描画の検証なしで残る（「No unique owned extraction range…」の QA）。表の上下の罫線の行は、Docling では表と別の text item（`#/texts/3307`–`3314`、読み順で表の直前）になる。これらは「Readable owned range omitted by correction」として本文ブロックになる。原本 PDF の描画（`#/tables/6` 付近）は、案の 19 行と空白を除いて一致する。（第2版で訂正）罫線文字は格子に乗らない。それでも、各文字の送りの終わりから次の文字までを測ると、空白数は案と 19 行すべてで一致する。
- **接続の失敗：** assemble の code continuation（mixed boundary）は、間に脚注だけを許す。`c212b` と `c213a` の間に罫線の本文ブロック8個があるため、「Unresolved outgoing／incoming code continuation」になる。診断で罫線ブロックを外すと、現行の assemble のまま接続された。表を出典とするコードへの接続自体は、188→189（`#/tables/5`）で既に成立している。**assemble の規則は変えなくてよい。**
- 70件中、表を出典とするコードは `c213a` と `code189`（p189、`#/tables/5`）の2件。描画行の検証に失敗しているコード案は 212 の他に p94・p112 がある。今回の規則変更でこれらに差が出る可能性がある（下の完了条件で照合する）。

## 要件・決定事項
1. **保証の範囲（ユーザー確認済み）。** 保証するのは 212→213 の1組である。ほかのページへの一般化は保証しない。ただし、全70件の再生で生じる変化は、すべて原画像と照合して説明できなければならない。不正な charspan は clip しない既存の契約を維持する。
2. **描画行の回復の入口（採用時、新方式だけ）。** `recover_listing` の条件を次の2点だけ広げる。それ以外の条件（同じページ、単一 provenance、body 層、図・隣接項目との重なりがない、範囲の間に省かれた文字がない、など）は維持する。
   - 読み順の連続性を判定するとき、子がすべて案の ref である list グループ（`#/groups/N`、label `list`）は、間に入っても連続とみなす。
   - section_header の項目も、案の evidence に含まれ、その描画行が案の行と一致する場合は、コードの行として扱う。
3. **描画行の検証（採用時、新方式だけ。第2版で変更、ユーザー確認済み）。** コードの行を等幅の格子で確かめるとき、次のようにする。
   - 格子の幅は、コードの中の格子に乗る文字（自身の送り幅が格子と同じ文字）の送りで決める（既存の方法）。格子に乗る文字がなければ、描画行を採用しない。
   - 格子に乗らない記号（自身の送り幅が格子と異なる描画文字。`→ ✓ │ ┌ ─` など）は、それ自体が描画されていれば行の文字として認める。
   - **行内の空白の数は、すべて描画で決める。** 行内で隣り合う2つの描画文字について、前の文字の送りの終わり（原点＋その文字自身の送り幅）から、次の文字の原点までの距離を測る。それが格子の整数倍（0 を含む）であれば、その整数を空白の数とする。前の文字が格子に乗る文字か記号かは問わない。抽出（生成空白の数）や AI 案の空白数とは一致しなくてよい。
   - 行頭の字下げは、従来どおり描画の格子から決める。
   - 1か所でも整数倍にならなければ、その案の描画行を採用しない（現行の扱い。許容誤差は、既存の格子の検査と同程度の最小のもの）。
   - **QA：** 格子に乗らない記号の直後の空白数を描画で決めた場合は、1つの QA を残す。evidence には、該当する行の描画位置を持たせる。文言は「格子外の記号の後の空白数は、描画の格子から決めた」という趣旨とする。
   - 非空白文字、行の数と順、行頭の字下げは、すべて描画と一致しなければならない。1つでも違えば、従来どおり回復しない。AI 案との照合は非空白文字と行で行い、行内の空白数の違いは不一致としない。
4. **表を出典とするコードの描画行（採用時、新方式だけ、ユーザー確認済み）。** 所有ページの表（`#/tables/N`、単一ページ・単一 provenance、文字範囲なし）だけを出典とするコード案は、原本 PDF の描画行で確かめる。表の範囲と、読み順で表に隣接する未所有のテキスト項目（罫線の行）からなる描画行が、要件3の規則で案の全行と一致する場合だけ、次のようにする。
   - 描画で決めた表示を採用し、各行の描画位置を evidence に残す。
   - 隣接する罫線のテキスト項目は、その行の出典としてコードに含める。本文ブロックにはしない（「Readable owned range omitted」にもしない）。
   - 一致しない、隣接項目が描画行の一部でない、他の所有ブロックと重なる、などの場合は、現行どおりとする（案のまま残し、QA を付ける。罫線の項目は本文ブロック）。
5. **接続は変えない。** assemble（`pdf_source.assemble_pdf_source`）の接続規則は変更しない。要件2〜4により、前半の最終行が回復し、間の罫線ブロックがなくなることで、既存の mixed boundary の規則で接続される。
6. **記録（新しい採用方式）。** 新しい採用方式名（例：`drawn-table-listing-v16`）と chunk schema 17 を追加する。保存要求・再利用・orphan 回収・`load_pdf_correction` は、既存の方式管理（`_RULE_VERSIONS`）で結び付ける。schema 16 以前の記録は旧規則で厳密に再読する。AI の回答の形式（`CorrectionAnswer`）は変えない。
7. **表示は変えない。** units と render の扱いは変えない。新しい QA 種別は、要件3の QA の文言だけとする。

## 動作確認方法
- **TDD（`tdd` Skill）：** 原因が確認済みで、自作 PDF による軽い local failing path がある。そのため、要件2・3・4に限って TDD を採用する。既存の未コミットのテスト（要件2）を引き継ぎ、要件3（第2版）の部分は、改めた期待で Red から始める。小さい自作 PDF（`tests/test_pdf_correction.py` の Courier の等幅行、別フォント・別の文字幅で描いた記号、表と罫線の行、ページをまたぐコード）を使い、公開の `correct_pdf → load_pdf_correction → assemble_pdf_source` で検証する。
  - 正例：①不正 charspan の最終行が list グループの子で、先頭が section_header のコードが、全行・字下げ・行内の連続空白つきで回復する。格子外記号の後の空白は描画の格子から決まり（抽出・案と数が異なる場合を含む）、要件3の QA が付く。②表を出典とする続きが描画行で確かめられ、隣接の罫線項目を所有し、前ページのコードと接続される。
  - Red：現行コードで、①が1行への縮約・最終行の欠落になり、②が Unresolved code continuation と罫線の本文ブロックになることを確認する。
  - 拒否の対照：完了条件の「拒否の対照」の各場合。
  - 方式の再読：schema 17 の保存・別 process の再読、schema 16 の記録の旧規則での再読を、既存の保存再読テストの形で少数押さえる。
- **非TDD：**
  - **全70件の再生：** verify-project の `pdf_preservation_comparison.py all` を、新規の 0700 親で、最終差分に対して1回実行する。最初の拒否で止めず全件を試行し、拒否が1件でもあれば比較に進まず停止する。比較の基準は `work/preservation-all-9drsIXYe/proof/`（#109 の最終再生、private）。採用差分と接続差分は、#101／#109 の Root 検証（`work/issue101-r4-root-verify-eso7WDLA/`、`work/issue101-r6-root-verify-BoGh9P9K/`、`work/issue109-root-verify-JcvqG9bO/`）と同じ方式で取る。方式名だけの差を分ける小さな helper の更新は、同じ保証の範囲で行ってよい。
  - **原画像との照合（Root が直接行う）：** 212–213枚目の原画像と、source・実 units・英語出力・QA を行ごとに照合する。変化したほかのブロック・組も、原画像と1つずつ照合する。
  - **人工 CLI：** verify-project の #97／#100 節の通常 run → fresh resume（実 Node／faux／no-network）を、別の新規親で実行する。
  - 実書籍の全翻訳、実 provider の起動、全組合せ E2E、新しい CI は行わない。
- **正式チェック：** CONTRIBUTING.md「変更影響から正式実行範囲を選ぶ」に従う。chunk schema と保存の共通部分を変えるため、Ruff check/format、PDF 環境の ty、core の全 pytest、正式 PDF phase を最終差分で実行する。
- **検証資産：** verify-project の「局所所有と全書籍の接続差分（#101）」節・#109 節と、`pdf_preservation_comparison.py`・`pdf_adoption_replay.py`・`pdf_connection_comparison.py` を再利用する。`pdf_preservation_comparison.py` の方式・schema の受け付けを更新する。#110 の照合手順と期待（要件・完了条件）を Feature Map の #110 節として、共通 `create-verification-skill` に従って最小限補う。Implementation Root は、同じ保証の範囲で、隔離した手段と小さい helper の作成・保存・再利用を判断してよい。
- **分担：** Worker は TDD・focused 回帰・全70件の再生・人工 CLI・Feature Map の更新と手順の再実行を行う。Root は別の新規の親として、212–213 と全変化の原画像照合、正式チェックの結果を直接確認する。版・入力の hash・コマンドと exit・比較結果・失敗を private に記録し、作成した一時ファイルと child だけを cleanup する。
- 許可された範囲で安全に操作できなければ、理由と再開条件を示して BLOCKED とする。保証・期待・公開契約の変更や、要件2〜4以外の新しい規則（assemble の接続規則の変更、charspan の補完など）が必要になったら REPLAN_REQUIRED とする。
